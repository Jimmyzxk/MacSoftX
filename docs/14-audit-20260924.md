## 2. 确认缺陷（已实证）

### P0-1 · release 构建在 `-warnings-as-errors` 下失败（构建/分发阻断）

- **位置**：`Sources/upmac/UI/SettingsView.swift:319`
- **问题**：`await masInstaller.runInstall(appState: AppState())` 新建了一个**临时 `AppState` 实例**，而非环境中的真实实例。
- **双重后果**：
  1. `SettingsView:13` 已有 `@EnvironmentObject var appState`，此处却造新实例 → release 优化下报 "weak reference will always be nil"，`-warnings-as-errors` 转为 **error**，`swift build -c release` 失败。
  2. 即便 debug 能过，`MasInstallService.runInstall` 成功后的 `await appState.reloadAll()`（`MasInstallService.swift:41`）刷新的是临时实例 → **UI 状态不更新**；且 `AppState.init` 内 `Task { await reloadAll() }` 触发一次**多余的全量重复扫描**。
- **实证**：
  ```
  swift build -c release -Xswiftc -warnings-as-errors
  → error: SettingsView.swift:319:40: weak reference will always be nil
  swift build -c release
  → warning: SettingsView.swift:319:40: weak reference will always be nil
  → Build complete! (16.10秒)  [0 errors, 1 warning]
  ```
- **修复**：改为 `await masInstaller.runInstall(appState: appState)`（用 `@EnvironmentObject` 注入的真实实例）。

### P0-2 · StateStore 损坏后被空字典静默覆盖，用户配置永久丢失

- **位置**：`Sources/upmac/Core/StateStore.swift:15-32`（`update`）、`:35-45`（`read`）
- **问题**：`update` 读文件失败（JSON 损坏 / 0 字节 / 权限）时 `dict` 保持 `[:]`，随后 `mutate(&dict)` + `out.write(... .atomic)` → **用只有一两个 key 的空字典整体覆盖原文件**。用户的 `ignoreRules` / `settings` / `extraScanDirs` / `caskCache` 全部丢失，**无备份、无提示**。
- **实证**（读码确认控制流）：`StateStore.swift:22-25` 读失败走 `[:]`，`:26` mutate，`:30` 无条件写回。
- **实证（权限）**：`ls -la ~/Library/Application Support/upmac/` → `-rw-r--r--`（0644），同机其他用户可读软件安装清单。
- **修复**：
  1. 读失败时把损坏文件重命名为 `state.json.corrupt-<ISO8601>` 保留，再以 `[:]` 继续。
  2. 引入 `state.json.bak`：成功写入后复制；读取失败回退 `.bak`。
  3. 写入后收紧权限至 `0o600`，目录 `0o700`。
  4. 补测试：写坏 JSON → `read()` 回退；`update()` 不丢已有 key。

### P0-3 · 全部来源失败时 UI 显示"所有软件均是最新版本"绿勾（状态不诚实）

- **位置**：`Sources/upmac/UI/ScanListView.swift:140`、`Sources/upmac/UI/MenuBarBubbleView.swift:53-66`
- **问题**：空态判断只看 `appState.items.isEmpty`，**不检查 `lastErrors`**。当所有 provider 全部失败（断网 / 包管理器损坏）时，`items` 空 + `lastErrors` 满 → 用户同时看到错误横幅**和**绿色"全部最新"勾，自相矛盾且严重误导。
- **对照**：`AllSoftwareView.swift:114` **已正确区分**（`items.isEmpty && !lastErrors.isEmpty` 走错误态）——ScanListView 与气泡缺失同样的判断。
- **实证**：读码确认 `ScanListView.swift:140` 为 `} else if appState.items.isEmpty { compactCelebrationState }`，错误横幅在其之前独立渲染，两者并存。
- **修复**：空态按 `items.isEmpty && lastErrors.isEmpty`（真最新，绿地）与 `items.isEmpty && !lastErrors.isEmpty`（扫描失败，红/橙地 + 重试入口）三分支。

### P0-4 · 卸载命令以字符串 split 重解析，名字含空格会执行错误命令

- **位置**：`Sources/upmac/Cleanup/UninstallService.swift:111-113`、`:201-214`
- **问题**：`resolveUninstallMethod` 拼出 `"brew uninstall --cask <name>"` 等字符串，执行时 `command.split(separator: " ")` 拆参数。`Inventory` 的 `name` 可能来自 `CFBundleDisplayName`（含空格，如 "Google Chrome"）并被误路由到包管理器分支 → 空格被拆成多个参数 → **执行错误的卸载命令**。
- **实证**：读码确认 split 路径存在（安全审计 §3-2 与稳定性 §6-#10 交叉确认）。
- **修复**：`resolveUninstallMethod` 改为返回 `[executable, [String]]` 参数元组，全程不经字符串 split。

## 3. 做得好的地方（保持，勿在重构中破坏）

1. **删除红线**：全部 `FileManager.trashItem`（3 处调用点），`Sources/` 内 `removeItem` / `rmdir` / `unlink` / `rm -` **零命中**；受管卸载失败**不 fallback 到文件删除**。
2. **零命令注入**：30 处 `ShellRunner.run` 全部 `Process.executableURL` + `arguments` 数组传参，无 `sh -c` 拼接；仅 4 处 `zsh -lc` 且命令字符串为硬编码常量。
3. **零提权**：无 `sudo` / `osascript` / `AuthorizationExecute`；需管理员的 gem 只显示"需管理员"徽章提示用户自行处理。
4. **零遥测**：无 analytics SDK、无本地日志落盘；唯一网络出口是 Homebrew 公共 Cask API，请求仅含归一化 app 名。
5. **零崩溃点**：`as!` / `try!` / `preconditionFailure` 全仓 0 处；唯一 `fatalError` 是 `NSViewRepresentable` 不可达 coder 路径。
6. **零永久 loading**：三处 `isLoading` / `isProcessing` 均有 `defer` 兜底。
7. **超时全覆盖**：29 处 `ShellRunner.run` 全部带 timeout（默认 30s），无无超时调用。
8. **UI 崩溃模式全清**：无嵌套 `NavigationSplitView`、`@StateObject` 位置正确、`ForEach` id 稳定、`frame` 无冲突、`onAppear` 无死循环。
9. **XXE 防护**：`AppcastFetcher.swift:70` `shouldResolveExternalEntities = false`。
10. **退出路径统一**：4 条退出路径均走 `requestQuit`，`willTerminateNotification` 覆盖全部退出。
11. **零外部 SwiftPM 依赖**：`Package.swift:18` `dependencies: []`，无供应链包风险。
12. **性能实测优秀**：热扫 2.15s（首扫 18.3s，npm 冷缓存），库存 136 项 0.47s，窄环境（模拟 GUI）零超时。

## 4. 已推翻的子代理结论（勿据此前"修复"）

| 子代理结论 | 裁决 | 证据 |
|---|---|---|
| P0：`LeftoverScanner.scanLeftovers` 在主线程冻结 UI | **误报** | 手写探针实测：从 `@MainActor` 上下文 `await` 一个 nonisolated `Sendable` 类的 async 方法，函数体在**全局执行器**运行（`进入时主线程=false 完成时主线程=false`），主线程同期 CPU 循环 0.269s 正常完成。Swift 5.7+ SE-0338 语义。若按报告用 `Task.detached` 包裹，反而引入嵌套脱离与数据竞争回归 |
| P0：`InventoryService.performScan` 在主线程做 O(A×C) 比对 | **误报**（同上一条推理） | `performScan` 为 `nonisolated static`（`InventoryService.swift:51`），同上不阻塞主线程。O(A×C) 本身是真实的 P2 性能债，但**不是**主线程冻结 |
| P1：uv 回退解析把 `Installed at:` 行误判为假更新项 | **误报** | 实机 `uv tool list` 输出为 `browser-use v0.13.10` + `- xxx` 子项格式，**无 `Installed at:` / `Updated:` 行**。`UvProvider.parse:22` 已过滤 `-` 开头与空行，当前 uv 版本下不会产生假项（保留黑名单加固作为跨版本防御） |
| P0：CLI 模式 `semaphore.wait()` 会永久挂死 | **降级为理论风险** | 已实证 CLI 路径无 `@MainActor` 依赖（`CaskInstaller` / `ScanMode` / `InventoryMode` 均非隔离），当前 4 次实跑（`--scan` ×2 / `--scan-fast` / `--inventory`）全部正常退出。但缺少超时兜底仍是 P2 |
| P0：`kill(-pid, SIGKILL)` 会误杀自身进程组 | **理论风险** | macOS 上无 PGID==pid 的组时 `kill(-pid)` 返回 ESRCH → 正确回落到 `process.terminate()`。仅当系统中恰好存在该 PGID 才触发，条件苛刻。移除 `kill(-pid)` 分支仍建议（见 P2-2 关联） |
